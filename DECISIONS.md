# Decisions Log

A running record of decisions made during planning, and the reasoning behind them. Add new entries at the top as the project evolves.

---

### Theming: CSS custom properties via Mantine cssVariablesResolver
**Decision:** All theme tokens are expressed as `--g-*` CSS custom properties injected by Mantine's `cssVariablesResolver`. Mantine's own body/surface variables (`--mantine-color-body`, `--mantine-color-dark-6/7`) are overridden in the same resolver so Mantine components automatically pick up the active theme without per-component overrides. Theme selection and dark/light mode are stored independently in `localStorage`.
**Why:** Keeps theme logic in one place (`ThemeProvider.tsx`) and makes tokens available globally as CSS variables — no prop-drilling or context reads needed in leaf components. `cssVariablesResolver` is the canonical Mantine extension point for this purpose, and `forceColorScheme` on `MantineProvider` ensures Mantine's dark/light mode is always in sync with the user's choice.

### Themes renamed from source material
**Decision:** All themes ship under app-specific names (Default, Cobalt DOS, Phosphor, Frostline, Nightshade, Canopy, Graphite, Amber). Internal IDs preserve the source mapping (modern, borland, terminal, nord, dracula, monokai, onedark, amber). Attribution is kept in `THEMES.md`, not in the UI.
**Why:** Avoids implying affiliation or endorsement with third-party projects (Dracula, Nord, Monokai, Atom One Dark). `THEMES.md` keeps the lineage visible internally.

### Frontend → API routing: Vite proxy (local dev) + reverse proxy (Docker)
**Decision:** In local dev, configure Vite's `server.proxy` to forward `/api/*` requests to the ASP.NET backend — no CORS setup needed. In Docker, put a lightweight reverse proxy (Caddy or nginx) in front of both the static frontend and the API, routing `/api/*` internally. Only the reverse proxy container has a published port.
**Why:** Keeps both environments same-origin, avoiding CORS entirely. Consistent mental model between dev and Docker. Matches the "one published port" principle in `SECURITY.md`.

### Primary keys: UUID
**Decision:** All tables use UUID (Guid) PKs, generated by the application (not the database).
**Why:** Postgres supports UUID natively; UUIDs are safe to generate client-side or in application code before a database round-trip, which simplifies EF Core inserts. Avoids integer ID enumeration in URLs even in a local-only app, and removes any future friction if data ever needs to merge across instances.

---

### Database: PostgreSQL over SQLite
**Decision:** Use PostgreSQL instead of SQLite.
**Why:** Room to grow (JSONB, arrays, full-text search, materialized views, better indexing), a chance to build real experience with it, and it's trivial to add as another Docker container alongside the app.

### Backend target: .NET 10
**Decision:** Target .NET 10 rather than .NET 9 or earlier.
**Why:** No reason to intentionally start on an older version for a project that won't have code written until .NET 10 is current.

### Frontend component library: Mantine over shadcn/ui
**Decision:** Use Mantine UI.
**Why:** Prior experience with shadcn/ui was minimal, so it wouldn't provide much of a head start. Mantine offers a large, polished, consistent component set out of the box (including `AppShell`, `Spotlight` command palette, forms, tables, notifications), letting effort go toward the application itself rather than building/maintaining UI primitives.

### No MediatR
**Decision:** Drop MediatR from the stack; use Vertical Slice Architecture without a mediator, via direct Minimal API endpoint logic.
**Why:** MediatR's license changed to a paid model requiring annual license management. Most usage only needed a small fraction of what MediatR provided anyway. Vertical Slice and MediatR are separable ideas — the folder-per-feature organization is kept, the mediator dispatch is dropped.

### Logic stays in the endpoint until it earns extraction
**Decision:** No default Services layer. Endpoint handlers contain their logic directly; extraction into a dedicated class happens only when logic is reused or a single file grows unwieldy.
**Why:** Avoids premature abstraction; keeps the codebase easy for both a human and an AI coding agent to trace end-to-end.

### Projects are hierarchical
**Decision:** Add a nullable `ParentProjectId` to Projects rather than a separate "Subprojects" concept.
**Why:** Gives unlimited nesting without a special-cased data model; most projects will only use one level, but the door isn't closed on more.

### Links generalized to Resources
**Decision:** Rename/expand "Links" to "Resources" with a `Type` field (Website, UNC Share, Local Folder/File, Git Repository, Documentation, Environment, Dashboard, Database, Other).
**Why:** Real-world project resources aren't just websites — UNC share documentation paths came up specifically as a need. A typed `Location` + `Type` model covers all of it without separate tables per resource kind.

### Wins log for performance reviews
**Decision:** Add a dedicated Wins entity, separate from completed Todos.
**Why:** Todos capture task completion; Wins capture accomplishments and impact worth surfacing at review time (compliments, resolved incidents, deployments, skills learned) — things that don't naturally fit as a "task."

### No authentication in v1
**Decision:** Ship v1 with no auth, assuming a trusted local Docker deployment.
**Why:** Single-user, local-only tool initially. Auth (Entra, GitHub OAuth, or local accounts) is deferred to a future phase rather than blocking v1.

### Idle-lock screen is a UI lock, not authentication
**Decision:** Add an idle-triggered, PIN-gated lock overlay (the Matrix-rain easter egg, evolved) that covers the whole app after a configurable idle timeout (default 5 minutes). The PIN, if set, is stored backend-side as a PBKDF2 hash+salt on `AppSettings` and required to dismiss the lock.
**Why:** Matches the "no authentication in v1" scope — this is a local screen lock for passerby privacy (someone glancing at or touching an unattended screen), not real authentication. There are no sessions, no JWT, and no protection against anyone with direct API access; the PIN only gates the frontend's own unlock flow.
